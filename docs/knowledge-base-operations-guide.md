# 企业知识库分级建设与管理说明书

本文用于指导公司内部按权限和范围建设、维护和使用知识库。

这份文档同时面向四类角色：

1. 普通员工
2. 项目成员
3. 部门负责人
4. 知识库管理员或系统管理员

## 一、先理解知识库为什么要分级

不是所有资料都应该直接放进“公司知识库”。

当前系统支持四级知识范围：

1. 个人知识库
2. 项目知识库
3. 部门知识库
4. 公司知识库

分级的目的有三个：

1. 让资料只在该看的范围内被看到
2. 让 AI 按权限调用正确的内容
3. 避免公司知识库被大量低质量、临时性内容污染

## 二、四级知识库分别放什么

### 1. 个人知识库

适合存放：

- 个人备忘
- 个人工作摘要
- 个人草稿
- 个人阶段性整理内容

不适合直接放：

- 全员制度
- 部门正式流程
- 公司统一标准

### 2. 项目知识库

适合存放：

- 项目方案
- 项目会议纪要
- 项目任务背景资料
- 项目专用模板
- 只在项目成员中共享的文档

### 3. 部门知识库

适合存放：

- 部门制度
- 部门 SOP
- 部门工作规范
- 部门常见问答
- 部门对内培训资料

### 4. 公司知识库

适合存放：

- 公司级制度
- 全员通用通知
- 公司统一规范
- 跨部门通用流程
- 需要全公司长期复用的正式资料

## 三、当前权限规则

当前系统的权限逻辑以组织架构和空间成员关系为基础。

按当前实现，可按下面理解：

| 知识范围 | 谁可以读取 | 谁可以维护 |
|------|------|------|
| 个人 | 本人、管理员 | 本人、管理员 |
| 项目 | 项目成员 | 项目成员、管理员 |
| 部门 | 该部门成员 | 部门负责人、管理员 |
| 公司 | 全体可读 | 部门负责人、公司管理员 |

使用时要牢记：

- 不是所有人都能写公司知识库
- 不是所有人都能改部门知识库
- 资料应先放到最小必要范围，再决定是否升级

## 四、最推荐的建设路径

正式资料不要一上来就放公司级。

推荐路径是：

1. 先在个人或项目范围整理
2. 稳定后升级到部门范围
3. 确认适合全员复用后，再升级到公司范围

这套方法的好处是：

1. 先控制质量
2. 再扩大影响面
3. 避免错误内容大范围扩散

## 五、普通员工怎么把内容交给 AI 使用

这部分是给普通员工的最简单流程。

### 场景 1：只是想让 AI 读取你当前的文件

操作步骤：

1. 在企业微信里把文件发给 AI 助手
2. 文件发完后，再发送你的要求
3. 例如：
   `请总结这份文件`
   `请提炼这份制度`
   `请参考这份文件帮我起草新版本`

说明：

- 这种方式适合即时处理
- 这种方式不等同于“正式建设分级知识库”

### 场景 2：想把一段文字沉淀为正式知识

推荐说法：

- `把下面内容保存到我的个人知识库，标题是 XXX`
- `把下面这段内容保存到项目知识库`
- `把这份总结保存到部门知识库`

建议做法：

1. 先把内容整理干净
2. 再明确写出归属范围
3. 再提供标题或主题词

### 场景 3：想确认知识是否已经可搜到

直接发送：

- `搜索一下 XXX`
- `帮我查一下刚才入库的内容`
- `在知识库里找一下 XXX`

## 六、知识库正式入库的标准做法

如果资料要长期保留、供多人复用、带权限控制，建议按正式流程处理。

正式流程建议由以下人员执行：

- 项目负责人
- 部门负责人
- 知识库管理员
- 系统管理员

## 七、四类知识库的详细入库方法

下面按范围分别说明。

### A. 个人知识库

适合对象：

- 普通员工
- 个人助理型使用场景

#### 方法 1：通过聊天沉淀文字内容

步骤：

1. 打开与 AI 助手的私聊
2. 发送整理好的内容
3. 明确说：
   `请保存到我的个人知识库`
4. 再用搜索验证：
   `搜索一下 XXX`

#### 适合放入的内容

- 自己常用的话术
- 个人工作笔记
- 个人阶段总结

### B. 项目知识库

适合对象：

- 项目成员
- 项目负责人

#### 方法 1：在项目群中沉淀项目资料

步骤：

1. 在项目群中 `@AI 助手`
2. 上传项目资料或直接发送文字
3. 明确说明：
   `请把这份内容沉淀到当前项目知识库`
4. 再让 AI 搜索验证

#### 方法 2：通过后台文件接口正式上传

适合知识库管理员或项目负责人操作。

当前接口支持把文件上传后直接索引到指定知识范围。

需要准备：

1. 文件本体
2. `user_id`
3. `space_id`
4. 归属范围 `knowledge_owner_type`
5. 归属 ID `knowledge_owner_id`

项目知识库推荐值：

- `knowledge_owner_type = project`
- `knowledge_owner_id = 项目 space_id`

### C. 部门知识库

适合对象：

- 部门负责人
- 部门知识维护人

#### 推荐入库顺序

1. 先整理内容
2. 先在个人或项目范围试用
3. 确认无误后再转为部门知识

#### 通过聊天沉淀部门知识的推荐说法

- `把下面内容保存到部门知识库，部门是 XXX`
- `请把这份部门流程整理后沉淀为部门知识`

#### 通过后台接口正式上传部门文档

推荐值：

- `knowledge_owner_type = department`
- `knowledge_owner_id = 部门ID或部门空间ID`

使用建议：

1. 仅放部门正式有效资料
2. 不要把讨论稿直接放部门知识库
3. 更新版本时要及时清理旧版本

### D. 公司知识库

适合对象：

- 部门负责人
- 公司管理员
- 知识库管理员

#### 公司级入库前必须先问自己三件事

1. 这份资料是否适合全员阅读
2. 这份资料是否已经稳定，不是临时草稿
3. 这份资料是否值得长期复用

如果有任意一个答案是否定的，不要直接入公司级。

#### 公司级正式上传推荐值

- `knowledge_owner_type = organization`
- `knowledge_owner_id = *`

说明：

- 组织级知识库的 owner_id 固定使用 `*`
- 这表示资料面向公司范围

## 八、后台正式上传文档到对应知识库的操作步骤

这一部分适合知识库管理员、项目负责人、部门负责人执行。

### 步骤 1：准备上传信息

需要准备：

1. 文件本体
2. 上传人 `user_id`
3. 存储所在空间 `space_id`
4. 知识归属类型 `knowledge_owner_type`
5. 知识归属 ID `knowledge_owner_id`

### 步骤 2：确定知识归属类型

可选值如下：

- `personal`
- `project`
- `department`
- `organization`

### 步骤 3：确定知识归属 ID

规则如下：

- 个人：默认可用当前 `user_id`
- 项目：通常填项目 `space_id`
- 部门：填写部门 ID 或部门空间 ID
- 公司：固定为 `*`

### 步骤 4：上传并索引

当前后台文件接口会在上传后自动进行文档索引。

文档索引成功后，系统会返回：

1. 文件路径
2. 文件名
3. 文件大小
4. 索引结果 `indexed`
5. 实际归属范围
6. 实际归属 ID

### 步骤 5：立即做搜索验证

上传完成后不要直接结束。

必须立刻验证：

1. 用文件标题搜索
2. 用文档中的关键词搜索
3. 用制度名、项目名、主题词搜索

这样可以确认：

1. 文档已成功提取文本
2. 文档已成功索引
3. 归属范围设置正确

## 九、如何管理知识库中的内容

知识库管理不是只管“加”，还要管“查、核、升、删”。

### 1. 查询

查询分两类：

- 搜索某个主题
- 列出某个范围下的全部条目

推荐顺序：

1. 先搜关键词
2. 再看条目列表
3. 再决定是否保留、升级或删除

### 2. 升级

升级就是把内容从较小范围提升到较大范围，例如：

- 个人 -> 项目
- 项目 -> 部门
- 部门 -> 公司

适合升级的内容：

- 已经验证有效
- 具有复用价值
- 已经不是临时草稿

不适合升级的内容：

- 未确认正确性
- 只适合单一场景
- 含明显时效性或临时决策

### 3. 删除

应该删除的内容包括：

1. 重复条目
2. 过期制度
3. 错误版本
4. 测试垃圾数据

删除前建议先确认三件事：

1. 这条内容是否已被新版本替代
2. 是否还有人依赖它
3. 是否需要先导出留档

### 4. 清理

建议定期做四项检查：

1. 重复检查
2. 过期检查
3. 权限检查
4. 搜索效果检查

## 十、知识库质量维护建议

### 建议 1：标题要稳定

不要用：

- `新版`
- `最终版`
- `先这样`

尽量用：

- 正式制度名
- 正式项目名
- 正式流程名

### 建议 2：关键词要统一

同一类资料尽量使用统一称呼。

例如：

- `报销制度`
- `车间通行管理规定`
- `内部沟通管理办法`

不要一会儿叫“沟通办法”，一会儿叫“内部沟通规定”，一会儿又叫“沟通制度草案”。

### 建议 3：先小范围，后大范围

不要跳过验证阶段直接上公司级。

### 建议 4：正式资料和临时资料分开

临时讨论、草稿、半成品不要与正式制度混在一起。

## 十一、最常见的错误做法

### 错误 1：所有资料都放公司知识库

后果：

- 搜索噪音大
- AI 容易引用不该全员使用的资料
- 后续维护成本很高

### 错误 2：不做验证就认为已入库

后果：

- 文档可能上传了，但没有成功索引
- 搜索可能根本找不到

### 错误 3：旧版本不清理

后果：

- AI 可能引用过期版本
- 用户看到多个冲突答案

### 错误 4：把临时聊天直接当正式知识

后果：

- 噪声知识越来越多
- 可复用性越来越差

## 十二、推荐的公司级分工

为了让知识库长期可用，建议按下面方式分工：

### 普通员工

负责：

- 提供原始资料
- 上传待分析文件
- 反馈搜索效果

### 项目成员

负责：

- 项目资料整理
- 项目知识沉淀
- 项目阶段性升级

### 部门负责人

负责：

- 部门制度审核
- 部门知识准入
- 部门知识清理与升级

### 知识库管理员

负责：

- 公司级知识准入
- 重复与过期内容治理
- 结构规范
- 索引验证与质量巡检

## 十三、建议执行的标准流程

推荐全公司统一采用下面这套流程：

1. 上传或整理原始资料
2. 先让 AI 总结、清洗、结构化
3. 先放到最小必要范围
4. 验证可搜索、可引用
5. 再决定是否升级范围
6. 定期清理旧版本和重复条目

## 十四、最后的原则

知识库不是“资料堆放区”，而是“可被 AI 准确调用的有效知识层”。

判断一条内容是否值得入库，只看三件事：

1. 是否正确
2. 是否稳定
3. 是否值得复用

如果三项里有一项不满足，先不要扩大范围。
