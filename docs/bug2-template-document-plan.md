# Bug 2 实施方案 — 模板文档生成链路改造

**日期**：2026-06-11  
**问题**：用户上传 `.docx` 模板后，系统生成的新文档没有稳定继承模板的章节结构、标题层级、编号格式、表格与版式意图。

---

## 1. 问题重述

当前链路是：

`上传模板 docx -> 提取纯文本 -> LLM 丰富 -> 新建空白 docx -> 启发式补标题样式`

这个链路的根问题不是“模型不够聪明”，而是模板在进入系统后已经被降级为纯文本：

- 标题样式丢失
- 编号规则丢失
- 表格结构丢失
- 页眉页脚/签字栏丢失
- 段落层级与模板意图丢失

因此，后续无论是 prompt 强化还是 OfficeCLI 简单写段落，都只能“猜模板”，不能真正“使用模板”。

---

## 2. 目标

我们希望把 Bug 2 的修复目标拆成三个层级：

### Level A：最小可行版

让系统至少能：

- 保留原始模板文件
- 提取模板的结构化大纲，而不只是纯文本
- 让 LLM 按结构化大纲生成内容
- 生成结果在章节结构、标题层级、编号顺序上明显优于当前版本

### Level B：稳妥版

在 Level A 基础上进一步做到：

- 区分“模板骨架”和“用户要求”
- 支持模板中的表格、固定段落、签字栏保留
- 对有明确占位符的模板进行定点填充

### Level C：完整版

在条件允许时做到：

- 直接以原始模板 docx 作为生成基底
- 最大程度保留模板样式、段落结构、页眉页脚、表格布局
- 针对不同类型模板形成统一的模板实例化机制

---

## 3. 三档方案

## 方案一：最小可行版

### 核心思路

不直接改“模板填充”，先改“模板理解”。

即：

`上传模板 -> 保存原始 docx -> 提取结构化大纲 -> LLM 按大纲生成 -> 按大纲写回 docx`

### 改造点

1. 在文件处理阶段保留原始模板文件路径，不再只保留提取后的纯文本。
2. 为 `.docx` 增加结构化提取器，至少输出：
   - 文档标题
   - Heading 1/2/3 层级
   - 编号段落
   - 普通正文段落
   - 表格文本占位
3. 在 `generate_document` 前，把模板输入改成两部分：
   - `template_outline`
   - `user_requirements`
4. 在生成 docx 时，不再只靠“首段 Heading1、短段 Heading2”的启发式，而是按 outline 类型写回。

### 优点

- 技术风险最低
- 不依赖模板里必须存在占位符
- 能较快显著改善“结构跑偏”问题

### 缺点

- 仍然不是严格意义上的“基于原模板填充”
- 页眉页脚、精细样式、复杂表格仍无法完整继承

### 适用场景

- 多数“制度/规范/通知/报告”类模板
- 模板主要价值在章节结构，而不是复杂排版

---

## 方案二：稳妥版

### 核心思路

在方案一基础上，增加“模板可填充性识别”：

- 有占位符的模板：走“定点填充”
- 无占位符的模板：走“结构化重建”

### 改造点

1. 新增模板扫描逻辑，识别常见占位符：
   - `{title}`
   - `{{content}}`
   - `【待填写】`
   - `_ _ _`
   - `XXX`
2. 给模板打标签：
   - `fillable_template`
   - `outline_template`
3. 对 `fillable_template`：
   - 使用 `python-docx` 做段落文本替换
   - 必要时对表格单元格做替换
4. 对 `outline_template`：
   - 退回方案一的结构化生成链路

### 优点

- 能兼容两类真实模板
- 相比“一刀切模板填充”更稳
- 团队可以逐步扩展占位符规则

### 缺点

- 需要维护模板分类逻辑
- 替换规则不统一时，模板适配成本会上升

### 适用场景

- 模板来源复杂、格式风格不统一
- 业务方经常上传“半成品模板”或“占位模板”

---

## 方案三：完整版

### 核心思路

把模板文档真正当作“基底文档实例”，而不是“参考文本”。

即：

`上传模板 -> 保存模板 -> 解析样式与结构 -> 在原模板上填充/扩写 -> 导出新文档`

### 改造点

1. 引入更完整的 docx 结构处理：
   - 段落样式
   - numbering 定义
   - 表格结构
   - 页眉页脚
   - 分节信息
2. 明确模板实例化协议：
   - 哪些段落可替换
   - 哪些段落需要保留
   - 哪些章节需要扩写
3. 对复杂模板建立业务模板规范：
   - 模板命名
   - 占位符写法
   - 表格约定
   - 签字栏约定

### 优点

- 最接近业务用户对“按模板生成”的预期
- 能最大化保留原模板风格

### 缺点

- 开发复杂度最高
- 测试样本要求高
- 对模板规范化要求高

### 适用场景

- 高频、固定格式、业务价值高的正式文书
- 例如合同、制度、审批附件、标准通知模板

---

## 4. 推荐顺序

建议团队不要直接跳到完整版，而是按下面顺序推进：

### 第 1 阶段：先做最小可行版

目标：

- 不再丢模板本体
- 能提取结构化大纲
- 让输出结果在结构上先稳定下来

这是当前最值得先做的版本，因为它能最快消除最主要的用户体感问题。

### 第 2 阶段：补稳妥版的模板分类

目标：

- 让“有占位符模板”和“无占位符模板”走不同链路
- 降低一条链路试图兼容所有模板的复杂度

### 第 3 阶段：只对高价值模板做完整版

目标：

- 不把整个系统一开始就做成通用复杂模板引擎
- 只在高频、高价值文书场景中推进真正的模板实例化

---

## 5. 具体实施建议

### 第一批建议改造的文件

- `src/gateway/wecom_file_handler.py`
  - 保留原始上传模板文件
  - 不再只返回文本预览
- `src/knowledge/document_converter.py`
  - 新增 docx 结构化提取方法
- `src/tools/builtin.py`
  - 将文档生成输入拆成“模板结构”和“用户要求”
- `src/tools/document_tool.py`
  - 按结构类型写回文档，而不是只靠长度启发式判断标题

### 新增中间数据结构建议

建议新增一个模板结构对象，例如：

```python
{
  "title": "车间通行管理规定",
  "sections": [
    {"level": 1, "type": "heading", "text": "第一章 总则"},
    {"level": 2, "type": "clause", "text": "第一条 目的"},
    {"level": 2, "type": "body", "text": "..."},
    {"type": "table", "rows": [...]}
  ],
  "placeholders": ["{title}", "{{content}}"],
  "template_mode": "outline_template"
}
```

这样后续不管是 LLM 生成、模板填充还是测试断言，都有稳定中间层。

---

## 6. 验收标准

建议讨论时不要只说“效果更好了”，而是用下面标准验收：

1. 对同一模板，输出文档的章节顺序与模板一致
2. 标题层级不再明显错乱
3. 编号样式不再大面积丢失或串级
4. 用户要求能覆盖模板中的占位内容
5. 长模板不再因 5000 字截断导致后半部分结构丢失
6. 至少有 3 类样例模板通过回归测试：
   - 制度类
   - 通知类
   - 带表格模板类

---

## 7. 风险提醒

### 风险 1：过早押注 OfficeCLI 模板填充

如果 OfficeCLI 对模板保真度和可编辑能力有限，直接押注它可能把方案带偏。建议先验证它是否适合“模板基底修改”，不行就尽早把模板填充交给 `python-docx`。

### 风险 2：把所有模板都当成统一模板

真实业务里模板差异很大。不要假设所有模板都有占位符，也不要假设所有模板都适合直接替换。

### 风险 3：继续依赖 prompt 修复结构问题

prompt 可以优化内容质量，但不能替代模板结构保留。结构问题应优先通过数据与链路修复。

---

## 8. 最终建议

推荐团队采用：

1. 先落地**最小可行版**
2. 紧接着补**模板分类的稳妥版**
3. 只对高价值模板推进**完整版**

一句话总结：

> 不要再把 Bug 2 当成“文案生成问题”，而要把它当成“模板保真链路缺失问题”来修。
